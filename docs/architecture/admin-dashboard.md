# World Manager (admin dashboard)

Separate client page at `/admin` (dev: `/admin.html`) for viewing server data and game content.

## Auth & API surface

Admin auth accepts **either** a signed-in session cookie **or** an `Authorization: Bearer` API token, resolved to one `AdminPrincipal` by `createAdminAuth()` and gated router-wide by `requireAdmin` (401 if unauthenticated or the token is bad, 403 if the caller isn't an admin). Roles are `admin` and `superadmin`; emails in `ADMIN_EMAILS` are automatically super admins, and super admins grant roles to anyone else from the Accounts tab. The full model — role resolution, token lifecycle, and which routes reject API tokens — lives in `docs/architecture/auth.md` → "Admin roles", "API tokens", and "Unified admin auth". API endpoints at `/api/admin/*` return runtime data (overview stats, accounts with online status) and full unfiltered game content (`GET /api/admin/content` returns all monsters, items, zones, and world data).

**Access surface** — `GET /api/admin/me` (the caller's identity and role, used to decide which super-admin-only controls to render), `PUT /api/admin/accounts/:email/role` (super admin + session only), and `GET/POST /api/admin/api-tokens` + `DELETE /api/admin/api-tokens/:id` (always scoped to the caller, session only). All are described in the admin OpenAPI spec under the **Access** tag.

**Assets (`/api/admin/assets/*`, `server/src/admin/assetRoutes.ts`)** — one surface for every kind of imagery the game serves, registered onto the same admin router so the router-wide `adminMiddleware` gate already covers it:

- `GET /assets` — the kind registry itself (`{ kinds: Record<kind, { kind, label, description, mount, dir, idFormat, shape, urlTemplate, fallbacks }>, maxBytes }`), so a client can discover kinds rather than hard-coding them.
- `GET /assets/coverage?kind=&includeEntries=true&missingOnly=true&limit=` — the "what's missing art?" report: per-kind `required`/`present`/`missing`/`coveredByFallback`/`overrides`/`orphans` plus a rolled-up `summary`, and optional per-id `entries`. See `docs/architecture/content.md` → "Artwork & imagery".
- `GET /assets/:kind` — every stored asset for a kind (`{ kind, count, assets }`), each with its public URL (cache-busted by mtime), byte size, and pixel dimensions.
- `GET /assets/:kind/:id` — metadata for one asset, 404 when there's no file.
- `POST /assets/:kind/:id` — upload/replace a PNG (multipart, field name `artwork`), returning `{ success: true, asset }`.
- `DELETE /assets/:kind/:id` — idempotent delete, returning `{ success: true, removed }`.

All of them go through `AssetStore` (`server/src/game/AssetStore.ts`), which validates the PNG signature + `IHDR` chunk (the client-declared mime type is never trusted), enforces the per-kind square-or-any shape rule and the 512 KB ceiling, and rejects any id that could resolve outside its kind's folder. Unknown kinds, validation failures, and oversized uploads all return `400 { error }` rather than an HTML error page. The same store backs the MCP asset tools — see `docs/architecture/mcp.md`. Every route above (and the deprecated aliases below) is also described in the admin OpenAPI spec, `server/src/admin/adminSwaggerSpec.ts`, browsable at `/api-docs/admin`.

**Deprecated**: `POST/DELETE /api/admin/artwork/:kind/:id` and `POST/DELETE /api/admin/items/:id/artwork` remain as thin aliases that delegate to `AssetStore`, so an older client build or a bookmarked script doesn't break mid-deploy. New callers should use `/api/admin/assets/*`.

## Layout & shell

Built as a separate Vite entry point (`admin.html`) isolated from the game client and styled with its own utilitarian theme (`styles/admin-theme.css`) — does NOT share `pixel-theme.css` with the game.

**Modular layout**: shell + per-tab modules under `client/src/admin/tabs/`, all sharing state via the `AdminContext` interface. The shell renders:

- A sticky **status bar** (always visible at the top with a version selector + Publish/Deploy/+New Draft buttons; creating a new draft auto-selects it so the UI immediately becomes editable).
- A left **sidebar** (collapsible to a hamburger menu under 900px wide; each item also shows a **UI Size selector** S/M/L/XL — value persisted to `localStorage['adminUiSize']` and applied as the `data-admin-size` attribute on `<html>` so the density tokens cascade). Tabs marked `footer: true` in `TABS` (`client/src/admin/types.ts`) render *below* the sidebar spacer in the utility cluster alongside UI Size and Refresh, rather than in the main content list — currently just **API Tokens**. They are ordinary tabs otherwise: `visibleTabs()` still governs reachability by URL and session restore.
- The active tab's content.

**Density tokens** (`--admin-pad-page-{x,y}`, `--admin-pad-cell-{x,y}`, `--admin-pad-section`, `--admin-pad-btn-{x,y}`, `--admin-pad-input-{x,y}`, `--admin-gap-loose`, `--admin-gap`, `--admin-gap-tight`, plus `--admin-sidebar-width` and `--admin-topbar-height`) scale with the UI size, so picking Small tightens every padding/gap on the page (table rows, fieldsets, modal padding, sidebar, topbar, etc.) — not just font size.

**All edit forms are popup modals** (Monsters, Items, Sets, Shops, Henchmen, Zones, Encounters, Tile Types, Dungeons, NPCs, Quests, Recipes) opened via `components/Modal.ts`; modal inputs use `--admin-bg-2` background by default with a focus state on `--admin-panel`.

**CRM artwork upload pipeline**: monsters, zones, tile types, and per-map backgrounds (`parchment`, keyed by `mapId`) share the same artwork upload UI inside their edit modal — see `client/src/admin/components/ArtworkSection.ts` (renders preview + file picker + upload/remove buttons, posting to `POST/DELETE /api/admin/assets/:kind/:id`). The Items tab still carries its own inline uploader on the deprecated item-specific alias; it writes to the same store. The upload preview refreshes straight from the response's `asset.url`, which is already stamped with the file's write time, so there's no cache-busting guess.

Those modals only cover the kinds that have an owning edit modal — the API itself covers **all 15 managed kinds** in the registry (including the ones with no content entity behind them: class portraits, NPC portraits, the splash logo, combat/room backdrops, and the class/slot/nav icon sets), which are uploadable via `/api/admin/assets/:kind/:id` or the MCP asset tools. **Adding a new kind is one row in `ASSET_KIND_INFO`** (`shared/src/assets/AssetKinds.ts`) — the Express static mount, the vite dev proxy entry, the upload allow-list, the client `AssetKind` union, and the coverage report all derive from it (a new kind also has to be listed in either `MANAGED_ASSET_KINDS` or `DEFERRED_ASSET_KINDS`, which a shared test enforces). Only a kind that wants an in-modal uploader additionally needs the `renderArtworkSection({ kind, id }) / wireArtworkSection(root, { kind, id })` pair in that tab's edit modal. See `docs/architecture/content.md` → "Artwork & imagery" for the kind table and fallback chains. Note that a per-room backdrop override (`combat-bg` / `room-bg`) is uploaded under the **room's GUID** (`WorldTileDefinition.id`), not the old `{zoneId}-{col}-{row}` composite — the composite can't tell two maps apart. Backdrops already uploaded under the composite keep rendering and still count as `overrides`, not `orphans`, in the coverage report.

Map management is split across two tabs (mirroring the entity-vs-editor split elsewhere): the **Maps** tab manages the *set* of maps, and the **Map Editor** tab edits the *rooms* of one selected map. The Map Editor viewer uses HTML5 Canvas with pan/zoom; room names show on all tiles (admin sees everything, no fog). A **map selector** dropdown at the top of the editor switches which map's canvas is shown (one `HexGrid` per `mapId`); the canvas and room sidebar are scoped to it. Editing controls (room edits, **+ Add transition**) are gated on draft mode — outside a draft they render **disabled with a "switch to a draft version" tooltip** rather than disappearing, so the capability stays discoverable. See `content.md` → Multi-map for the data model.

## Per-tab notes

- **Overview**: analytics placeholders (DAU, retention, level distribution, class mix) — coming soon.
- **Versions**: below the version table, selecting a version renders a read-only "Design Notes" panel (`ctx.versionContent.designNotes`) — one card per note (title, author · date, markdown body, tags). Notes are recorded via the MCP content-authoring tools (`save_note`/`delete_note`), not editable here — see `docs/architecture/mcp.md`.
- **Accounts**: defaults to sort-by-Created desc, has filters (hide no-character accounts, active-in-last-N-days, created-in-last-N-days) with live filtered count. Admins carry an `Admin`/`Super Admin` pill in the Status column. Clicking a username opens a detail modal with session history, duplicate device token detection (highlighted), deactivate/reactivate buttons, a reactivation request viewer, and an **Admin Role** row. That row is an editable dropdown (None / Admin / Super Admin) only for a super admin viewing someone else; it renders as read-only text for a plain admin, for an `ADMIN_EMAILS` account ("from ADMIN_EMAILS"), and for your own account — matching the server-side guards exactly.
- **API Tokens** (`ApiTokensTab`, sidebar footer cluster): your own bearer tokens for the MCP server and the admin API — nobody else's are visible here or over the API. Label + optional expiry date, then Generate; the plaintext secret appears in a one-time modal with copy buttons for both the raw token and a ready-to-paste MCP client config, since it is stored hashed and can never be shown again. The table lists label, token prefix, created, expiry (expired rows dimmed), and last-used, with per-row Revoke.
- **Invite List**: only appears in the sidebar when the server has `INVITE_ONLY=true` (fetched once at startup via `GET /api/admin/invite-list`; hidden entirely — not disabled-with-tooltip — when the env var is off, and unreachable by direct tab URL/session-restore in that state too). Simple email input + Add button and a table of currently-invited emails with per-row Remove — no modal. See `docs/architecture/auth.md` for the login-time gating logic.
- **Tile Types**: shows real hex-shaped tile previews (non-traversable types render with a red hex ring around the colored hex — the canvas map keeps its own red-X marker); IDs are hidden in the UI and auto-generated as GUIDs on create — only the tile name is editable. The color picker hex code is hidden until the picker is focused. An **Entry Requirements** fieldset sets the type's default gate (required item, min level, required quests) — see `content.md` → Room entry requirements. The card tag summarizes the gate.
- **Maps** (`MapsTab`): table of every map (name, id, room count, a **Default** badge on the spawn map) with **+ New Map** (name + auto-derived id), **Edit**, and **Del** (blocked on the default map, maps with rooms, or maps with inbound transitions). Backed by `POST/DELETE /api/admin/world/map` (`?versionId=` for drafts). **Edit** opens a modal with the map name (rename keeps the existing start tile; draft-only) plus a **map background (`parchment`) uploader** — the tiling texture drawn behind the map, served at `/parchment-artwork/{mapId}.png` and loaded per-map by the client. Artwork is a live global asset (not versioned), so the uploader works regardless of draft mode; the name rename and Del are draft-gated (disabled-with-tooltip otherwise).
- **Map Editor** (`MapTab`): the room/canvas editor for the map chosen in the selector. Sidebar opens the room editor directly when a tile is clicked (no preview/edit toggle); Backspace/Delete deletes the selected room when not focused in a field. "Set as Start Tile" sets the selected map's start (also the global spawn for the default map). The room editor's **Map Transitions** section links a room to one or more rooms on other maps: click "+ Add transition" to enter pick mode (a banner appears), switch the map selector to the destination map, then click the destination room — the link is appended to the source room's `transitions[]` and a 🕳️ glyph marks linked rooms. Each existing transition lists its destination with a "Remove" button, plus a 🔒 summary when that exit carries its own gate (per-transition gates are authored via MCP, not here). Esc cancels pick mode. The room editor also has an **Entry Requirements** fieldset — the same shared `components/EntryRequirements.ts` editor the Tile Types form uses — which overrides the tile type's gate field by field; saving writes `entryRequirements` and clears the legacy `requiredItemId` so a room never carries two competing item requirements. Routes: `PUT/DELETE /api/admin/world/tile` (carries `mapId`/`transitions`) and `PUT /api/admin/world/start-tile` (optional `mapId`); all support `?versionId=`.
- **Shop edit modal**: sorts items alphabetically and includes a search box plus a "Show only stocked" toggle to filter the inventory checklist.
- **Dungeons**: list table with a modal form that supports floors (with grid shape, encounter table, per-floor rewards, boss flag), entry requirements (level/item/classes/party size), and first-clear rewards (flat bonus XP/gold + item rewards). Every item reward row (floor or first-clear) has per-reward class checkboxes ("none = any") so loot can be routed by class.
- **Skills** (`SkillsTab`): the skill tree editor (issue #267) — skills are versioned content. Per-class tables (unlock level or grant-only badge, type pill, options summary, cooldown) with draft-gated Add/Edit/Del, a per-class **Edit Slots** modal (slot schedule: type + unlock level per slot), and a **Restore default skills** action (`POST /api/admin/skills/seed`; overwrites seed-id skills back to defaults, keeps custom skills). The skill modal composes effect **options** from `SKILL_OPTION_CATALOG` via an inline searchable picker (filtered by search text and slot-type legality — active kinds only on active skills); param inputs are generated from each option's catalog spec (percent params edited ×100, stored as 0–1), and `validateSkillDefinition` runs client-side before PUT and server-side on every PUT. The Items and Sets edit modals gained searchable "Grants skills" checklists (`grantedSkillIds`; per-breakpoint for sets). Deleting a skill is blocked while any item/set grants it.
- **Game** link in the sidebar opens the game in a new tab.
