# Client shell, screens, and rendering

## Multi-screen app shell

DOM-based screen switching. `ScreenManager` handles show/hide with `onActivate`/`onDeactivate` lifecycle and writes `body[data-active-screen]`. Combat is the default screen; Map lazy-loads three.js and creates the world map on first visit. `#app` holds, in DOM order: `#top-hud`, `#persistent-xp-bar`, `#bottom-nav`, `#screen-container`, `#utility-strip`, `#chat-popout-root`. The nav comes before the screens so the rail is first in Tab order; `order: 1` puts the phone bar back at the bottom. `#app { isolation: isolate }` keeps every shell z-index below the body-level modals. `index.html` uses `viewport-fit=cover`; every edge element pads with the safe-area tokens (`--safe-top/-bottom/-left/-right`), and overlay offsets use `--hud-total` (HUD + safe top) and `--nav-total` (nav + `--nav-float-gap`, now 0, + safe bottom).

Three layouts of the same DOM (`client/src/styles/shell.css`):

- **Phone**: a column. HUD 44px, XP hairline 3px, the screen, utility strip 36px (the chat sheet takes its place while open), nav 56px.
- **Desktop** (`min-width: 860px`): `#app` becomes a grid with the HUD (48px) and XP hairline across the top, then an 84px rail, main, and the docked chat column (300px below 1024px, 340px from there). The strip is hidden. Closing chat frees its column.
- **Short landscape** (`orientation: landscape` and `max-height: 500px`): the same grid with a 40px HUD, a 56px icon-only rail whose tabs flex to fit and a 280px chat column. The rail's Settings tab is hidden, because the HUD avatar reaches it.

On the grid the rail and the docked column absorb the side insets, so `#screen-container` resets `--safe-left` to 0, and `--safe-right` to 0 while the column is open. A fixed overlay mounted inside main reaches the viewport edges anyway and must restore the real insets by joining the `:is()` list in `shell.css` (`.room-view-overlay`, `.item-popup-overlay` today).

Inactive screens use `content-visibility: hidden` plus `visibility: hidden` rather than `display: none` (under `@supports`). They keep their boxes, so a return visit doesn't rebuild style and layout from nothing, and a `ResizeObserver` on the screen itself still fires.

**Idle prebuild.** A first visit would otherwise pay for everything a hidden screen skips, and much of that is first-use font work later visits don't repeat. So `App.enterGame` hands `ScreenManager.prebuildSteps(['items', 'craft'])` to `runStepsWhenIdle` (`client/src/ui/idleSteps.ts`). Each screen gets two steps, each in its own idle slot: `Screen.prebuild()` renders the latest state without subscribing or sending, then `layOutWhileHidden` forces one layout with `data-prebuilding` set. `shell.css` uses that attribute to lift `content-visibility: hidden` from the screen and `auto` from the first 30 cards of each list. The attribute comes off in the same task, so nothing paints. A hidden screen can't be pressed, so these renders need no `deferWhilePressed`.

- **Once per game session.** Nothing re-arms it, and state pushes don't touch a screen that isn't active. A prebuilt screen can therefore go stale; its first `onActivate` writes only what changed.
- **Never in a hidden tab.** A step waits for `visibilitychange` and resumes when the tab is shown. `preloadMapCode` uses the same helper, and so should any new idle startup work.
- **Skipped** for a screen shown in the meantime and when Save-Data is on. Without `requestIdleCallback` (Safari) a 1.5 s timer stands in. Without `content-visibility`, hidden screens are `display: none` and the layout step does nothing.
- **No data.** A hidden screen must fetch no art, so item squares, slot icons and the Hero portrait use `loading="lazy"`. An image already known to have loaded renders eagerly, so a re-render doesn't flicker.

**Top HUD** (`client/src/ui/TopHud.ts`, constructed in `App.enterGame()` next to `PersistentXpBar`), left to right:

- Class avatar (`artworkUrl('class', …)` with class-icon fallback), level badge and a small gear mark: `data-nav="settings"`.
- Two status lines (`hudStatus`): `data-nav="map"`. Line one is the room. Line two is the first match of `Reconnecting…`, `→ {destination} · N rooms` (`routeSummary`; the destination is named only once explored), `{dungeon} · Floor x/y`, then the zone. On Battle, CSS swaps the status for the username because the combat header latches the location. On Map, the route line swaps to the zone while the route chip is up.
- Gold chip (`formatGoldChip`: full number below 10 000, else `12.3k` / `1.2M`): `data-nav="items"`.
- `.top-hud-bell-slot`, which `NotificationCenter` mounts its bell into.

The HUD and nav stay hidden until the player has a character and are hidden again on suspension. `PersistentXpBar` is only the hairline, filled by `scaleX`; the HUD badge shows the level and the raw numbers live on Hero › Stats.

**Utility strip** (`client/src/ui/UtilityStrip.ts`): the phone row above the nav. `#chat-strip-slot` holds the chat preview (see Chat) and a 48px Quests button carries the ready count. CSS hides the strip while chat is open and on the grid.

**Shared components**: `Segments.ts` (`renderSegments(items, activeId)`, a sticky `.ui-segments` tablist whose badge is a count for a number and a dot for `true`; `wireSegments(root, onSelect)` delegates clicks and arrow keys), `ConfirmDialog.ts` (`confirmDialog({title, body, confirmLabel, cancelLabel, danger}): Promise<boolean>` on ModalStack; the player client has no `window.confirm`), and in `components.css` `.ui-row` (56px: 40px media, title and sub, actions), `.ui-section-label`, `.ui-empty` and a shared `@media (hover: hover)` block that uses highlights and brightness only.

## Navigation

`BottomNav` (`client/src/ui/BottomNav.ts`, tabs from `NAV_TABS` in `App.ts`) is one element laid out by CSS as the phone bar or the rail. The bar is flat and full width with five always-labelled tabs: **Map, Hero** (screen id `items`), **Battle** (`combat`), **Craft, Social**. `data-rail-only` tabs add **Quests, Chat, Settings** on the rail.

- **Map, Hero, Battle, Craft, Social, Settings** switch screens through `navigate`. Re-tapping Map recentres on the party.
- **Quests** opens the Quest Log, and **Chat** toggles chat. Neither changes screen. Chat lights `overlay-active`, a neutral plate around its icon, distinct from `active`'s gold bar and label.

**Battle** is a red disc inside the bar: 37px on phones with the label below it, 44px on the rail, 36px on the icon rail. While fighting it shows a static gold ring (`fighting-pulse`, no infinite animation); victory and defeat flash once. A `has-path` dot on Map marks a route in progress and works without art. Badges: Social dot (friend requests or party invites), Hero dot (mailbox items or a trade waiting on you), Quests count (ready to turn in), Chat count (unread). Every button carries `aria-label`, extended with what its badge says.

Nav icons are content: `navIconHtml(id, label, glyph)` renders an emoji glyph (`.nav-icon-glyph`: 🗺️ 🎒 ⚔️ 🔨 👥 📜 💬 ⚙️) with the `/nav-icons/{id}.png` image on top; the image fades in on load (adding `.has-art`, which hides the glyph) and removes itself on error, so a server with no nav art still shows icons. `quests` and `chat` are in `NAV_ICON_IDS` (`server/src/game/AssetCoverage.ts`), so the coverage report asks for them too.

**`navigate(screenId, sub?)`** (`client/src/ui/navigate.ts`) is the one way to change game screen: it closes transient UI (notification dropdown, Quest Log, a chat that covers the screen), calls `screen.setSubTab?.(sub)`, `switchTo`, `nav.setActive`, and saves `activeScreen` in sessionStorage. Unknown ids go to Battle; legacy `character` maps to `items`. `installNavDelegate` adds a capture listener so any `[data-nav="screen:sub"]` element navigates, which lets screens cross-link without touching `App` (`items:skills`, for example). `Screen.setSubTab` is implemented by Hero (`gear|skills|stats`) and Social (`party|guild|friends|ranks`).

**Back** (`installBackHandler`): one sentinel `history.pushState`, URL unchanged. Each Back pops it and runs the first that applies: `dismissTop()` closes the top overlay; the chat column closes in short landscape (the sheet and full layouts are on ModalStack, and a taller desktop column stays unless a touch keyboard is up); a screen other than Battle goes to Battle; otherwise `history.back()` leaves the app. Anything handled re-arms the sentinel. With no earlier history entry the app simply stays, and the next primary `pointerdown` restores the sentinel so the following Back is caught again.

**Escape** (`installEscapeHandler`): a window listener runs `dismissTop()` unless `defaultPrevented`. `BestiaryModal`, `DungeonEntryPopup` and `RecapModal` keep their own document handlers and call `preventDefault`.

**Where things live**:

- Hero › Gear: gear, inventory, mailbox, trades. Hero › Skills: the loadout; an empty skill bar links here. Hero › Stats: stats, XP numbers, Bestiary card.
- Quest Log: strip button or rail; owned by `App`.
- Social: Party, Guild, Friends and Ranks segments.
- Chat: strip or rail, docked column on desktop.
- Notifications: the bell.
- Settings: HUD avatar or rail. Player Options, notification preferences, Patch Notes, Sign Out.

## Per-player game state

Each player has a `PlayerSession` with character state, unlocks, combat log, and social data. Combat and movement are managed per-party by `PartyBattleManager`, which owns a shared `ServerParty` + `ServerBattleTimer` for each party. `PlayerSession` delegates battle/position queries to `PartyBattleManager` via callbacks wired by `PlayerManager`. Sessions persist when disconnected (battles keep running). `PlayerManager` maps usernames to sessions and WebSockets to usernames. Multiple connections per username are supported.

## GameClient subscriber pattern

`subscribe(cb, { replay? })` / `onCombat(cb)` / `onConnection(cb)` return unsubscribe functions. Multiple screens listen concurrently. Connection is deferred until `connect()` is called (after auth). `lastState` and `lastCombat` cache the newest `state` and `combat` messages. `lastState` is always a whole state, even though a push on the wire usually isn't (see WebSocket data use).

State pushes are rare mid-fight (battle start, result, move, user actions), so a widget that mounts after the first push would otherwise stay blank until the next one. Pass `{ replay: true }` to receive the cached `lastState` immediately on subscribe — the shell widgets (`TopHud`, `PersistentXpBar`, `BottomNav`, `UtilityStrip`, `NotificationCenter`) and `ChatPopout` do. `GameClient` also owns `combatLog` (a `CombatLogBuffer`, see Combat screen) and fills it from every state and combat message whether or not the combat screen is showing, and `sendCombatView(visible)` (deduplicated, re-sent when the socket reopens).

Other per-connection duties:

- **Presence.** `presence { visible }` is sent on every socket open and every `visibilitychange`, before `request_state` (separate from `combat_view`); the server uses it for the "while you were away" recap (see `combat.md`).
- **Forecasts.** `requestForecast(target)` returns the cached reply or `null` and sends `request_forecast`. Cache key = `forecastTargetKey(target)|partyKey`; `FORECAST_TTL_MS` 60 s (10 s for `unavailable`, `pending` never cached); at most one request in flight per target, retried after 15 s and re-sent on reconnect. The server keeps one explicit forecast per player, so a request for another target drops the older one: an `unavailable` reply for a target that is no longer the last one requested is passed to listeners but never cached, a target whose outstanding request was overtaken that way is asked for again, and the dropped request's reply is ignored while a newer request for the same target is in flight; a reply computed for an older party key triggers one automatic re-request. `peekForecast(target)` returns the latest `ok` reply whatever its party key or age — an `unavailable` reply (rate limit, dropped job) never replaces it, so `MapScreen` and `DungeonEntryPopup` render `unavailable` as that last estimate, dimmed with "updating…" (nothing when there is none); `denied` hides the forecast. `onForecast(cb)` delivers every `forecast` message, including pushed `{kind:'battle'}` live forecasts.
- **Bestiary.** `requestBestiary()` / `onBestiary(cb)` / `lastBestiary`. `requestBestiary()` returns the cached list while its version matches `character.mastery.version`, otherwise sends `request_bestiary` (at most once per 15 s while outstanding; re-sent on reconnect). Callers: opening `BestiaryModal`, activating the Hero screen, and `MasteryToasts` on a snapshot. Between fetches the views merge `character.mastery.recent` (fresher) over the full list.
- **Combat prefs.** `sendSetCombatPrefs(pct)`.
- **Recap.** `lastRecap` / `lastRecapItemDefinitions` come from each state; `onRecap(cb)` replays on subscribe, fires once per recap id and with `null` when the recap clears (so other tabs close their modal); `sendAckRecap(id)` drops that id locally even if the server still sends it for a moment.

`sendRaw` returns `false` when the socket isn't open and the message was dropped; `sendMove`, `sendEnterTransition`, `sendSetClass`, `sendAcceptQuest`, `sendTurnInQuest`, `sendEnterDungeon`, `sendShopBuy`, `sendShopSell` and `sendChat` return it so their UI can say so at once (`OFFLINE_NOTICE`, "You're offline — reconnecting. Try again in a moment.") instead of waiting on a reply that will never come. `onServerError` listeners receive `(message, code?, detail?)`; `detail.questId` correlates a `quest_refused` error with the quest that was refused.

## WebSocket data use

Three kinds of message carry almost all the traffic: state pushes (event-driven, up to about one a second while a party walks and wins quickly), the live `combat` stream (up to five a second, only to sockets showing combat, see `combat.md`), and anything triggered by the player. Three measures keep them small on mobile data.

**State pushes leave out what the socket already holds.** `PlayerManager.sendStateToPlayer` builds the whole state as before, then `server/src/game/StatePush.ts` serialises each top-level field once and fingerprints it. For each socket, a field whose fingerprint matches what that socket last received is left out and named in `unchangedFields`. `GameClient` calls `restoreElidedState` before it stores or fans out the message, so `lastState`, every subscriber and `{ replay: true }` see a complete state and nothing downstream knows about this.

- A socket's first push is always whole, because fingerprints are per socket and start empty. That covers reconnects and second tabs. A socket delivers in order and doesn't lose messages while open, so the client's copy can't drift from what the server recorded.
- Absent means gone. A field neither sent nor named (`shopDefinition` after leaving the shop) disappears from `lastState`, and the server forgets its fingerprint so its return is sent whole.
- Fields of 64 bytes of JSON or less always go out, since naming one would save nothing.
- A socket only gets partial pushes if its URL asks for them (`PARTIAL_STATE_PARAM`). A service worker can still serve an older bundle, and that bundle gets whole states, so any change to this wire format needs a new parameter value.
- A socket more than 64 KiB behind (`STATE_BACKPRESSURE_BYTES`) skips the push. Nothing is recorded as sent, so a later push carries whatever changed, and that socket alone is retried after `STATE_RETRY_MS`, because mid-fight nothing else may push for minutes. The player's other sockets aren't pushed to again, and no state is built until the socket has drained. This matters with compression on: sends wait for zlib instead of going out at once, so on a saturated server an unbounded queue would grow in memory rather than just running late.
- No field list to maintain: a new top-level state field takes part automatically. A field only saves anything if its JSON is stable, so keep clocks out of big fields. That's why the recipe list and its item definitions live in `craftingCatalog`, apart from `crafting`, whose `activeProgress.elapsedMs` changes on every push while a job runs.
- **State objects are shared between pushes.** An unchanged field is the same object in consecutive states, so subscribers must never mutate state; copy before sorting.

**Rosters go out as changes, and only as far as anyone looks.** `otherPlayers`, `social.allPlayers` and `social.onlinePlayers` grow with the population, and `otherPlayers` changes whenever anyone moves, so they would be re-sent on most pushes, and building and serialising them per push was the largest cost on the main thread. `SharedRosters` (`server/src/game/SharedRosters.ts`) builds them for everyone at once and serialises each entry once. Each socket's push then has a `rosters` field naming what that socket is missing, as `whole` or as `upserts` and `removes`. `restoreElidedState` applies it, so `lastState` and subscribers see whole lists as before.

- **`otherPlayers` holds the viewer's zone only.** That's as far as anything looks: the map skips anyone outside `currentZone`, the room lists and the Ranks room and zone filters are limited to the viewer's room or zone, and the class lookup in `SocialScreen` falls back to `allPlayers`. Anything new that needs players further away has to change this first. `allPlayers` stays global, because Ranks, friend search and chat need all of it.
- A roster missing from `rosters` hasn't changed. The field itself is always there on a partial push, and a state without it holds its own rosters (the whole-state path above). So `otherPlayers` and the two `social` lists are empty on the wire, and `PlayerSession` leaves them empty because it builds `social` more often than it pushes.
- The roster for a zone includes the viewer, since every socket in that zone shares it. `restoreElidedState` drops them.
- A socket gets a whole copy when it's new, when it changes zone, when more than half the roster changed since its copy, or when it's further behind than the change log reaches. The log is kept in proportion to the roster, so a roster's memory stays bounded.
- Rosters may be up to `ROSTER_REFRESH_MS` (100 ms) old, far less than the gap between one player's pushes, which is when they'd see it anyway. A connect or disconnect rebuilds them for the next push.
- Like field elision, this records what a socket holds only when a message really goes out, so a skipped push is caught up by a later one.

**Messages are compressed.** `server/src/wsServerOptions.ts` turns on `perMessageDeflate` at level 3 with `memLevel` 7, and caps inbound messages at 64 KiB because a small compressed frame can inflate to whatever the cap allows.

- Keep context takeover on. Consecutive pushes are nearly identical, so it's what makes small state and combat messages compress at all, and `ws` keeps each socket's deflate context allocated whether or not takeover is on (it resets the context rather than freeing it), so turning it off costs data and saves no memory.
- `threshold` does nothing here: `ws` only applies it without takeover, so every message is compressed.
- Don't set a numeric `clientMaxWindowBits`: `ws` then refuses any offer that doesn't name that parameter, and that client silently goes uncompressed.
- Every socket keeps an `error` listener, as `ws` expects; `close` follows the error, so nothing else needs cleaning up.

**What it adds up to.** One client against the real server on a synthetic world (100 recipes, 40 owned items), counting TCP payload, so TLS and packet headers come on top:

| Bytes per second | Before | Unchanged fields left out | Also compressed |
| --- | --- | --- | --- |
| Fresh character on the seed world | 1,932 | about 1,530 | 116 |
| Large catalogue, fights of about 15 s | 9,596 | about 1,590 | 120 |
| Large catalogue, fast fights | 48,036 | 3,139 | 199 |
| Fast fights, a screen without combat | 43,453 | about 2,460 | 134 |

A reconnect pays for one whole state: 71 KB, or about 10.5 KB compressed.

**Cost at the 1000-player soft cap.** Compression alone, replaying recorded streams to 1000 real sockets: about 0.3 MB per socket, and 0.4 to 1.8 cores in total depending on the stream, mostly on the libuv threadpool, with no meaningful added lag. It holds up only while the main thread has headroom. Sends wait for zlib, so past saturation they queue instead of just running late: lag gets several times worse, and memory reached about 1.2 GB at 1000 sockets after 5 minutes with the state-push limit above, against 2.9 GB after under 2 minutes without it. On a synthetic world at a fast fight pace, with rosters shared and sent as changes, 1000 players take 88 to 91% of the main thread with a round trip p50 of about 14 ms, against saturation and about 7 s when rosters were built and serialised per push, and each client gets 250 to 490 B/s. What's left on the main thread is mostly serialising each player's own state on every push: `prepareStatePush` and its hashing are about a third of the samples.

## State-driven re-rendering

Full state pushes are event-driven (battle start and result, moves, player actions; live combat has its own stream, see `combat.md`), so one can land at any moment, and `GameClient` fans each push out to every subscriber synchronously. A subscriber that rebuilds its DOM on a push can therefore replace a button between the player's press and release. Browsers don't deliver a click whose pressed element was removed, so the click is silently lost — the cause of #398 ("Accept does nothing"), and of a string of earlier one-off fixes.

`client/src/ui/render.ts` holds the two primitives every state-driven component uses:

- **`deferWhilePressed(root, paint)`** runs `paint` now, or — while a pointer press that started inside `root` is in flight — holds it until that press's click has run, then runs only the latest held paint for that root. Document-level capture listeners track the press: the flush happens on a macrotask after `click` (so the click's own handlers see the DOM the player pressed), 400 ms after a `pointerup` with no click, at once on `pointercancel` (a scroll took over) or window blur, and after at most 5 s. A press outside `root` never holds it, so map pans don't freeze panels.
- **`setHtml(el, html)`** writes `innerHTML` only when it differs from what `setHtml` last wrote to `el`, so identical pushes keep the same nodes (hover, focus, scroll and image loads survive). It returns whether it wrote.

Rules for adopters:

- Wrap only renders that are *not* the player's own action — state subscriptions, server-error and notification listeners, timers. A render inside a click handler stays immediate.
- Wrap the whole subscription body, read `gameClient.lastState` at flush time, and re-check visibility: the click that ended the press may have closed the component.
- Every write to a `setHtml`-managed element goes through `setHtml`, including clearing it on hide; a raw `innerHTML` write desyncs the cache and the next identical render is skipped. A region patched in place stays out of `setHtml` (the chat timeline, rank rows) or resets it before the next write (the bag after a count badge was patched).
- Prefer one delegated click listener on a stable root over per-render listener wiring.

An equality guard alone isn't enough: components that show live numbers (gold, inventory counts, quest progress, relative times) really do change mid-press, which is what `deferWhilePressed` covers. Adopters: `NpcTalkPopup`, `ShopPopup`, `DungeonEntryPopup`, `CharItemsScreen`, `CraftingScreen`, `SettingsScreen` (row values), `NotificationPreferences` (the late re-render), `NotificationCenter` (the open dropdown's list; the badge updates immediately), `SocialScreen` (segments, panel and trade modal), `ChatPopout` (timeline paints and the thread list; filter clicks render directly), `ChatStrip`, `TopHud` (the avatar), `CombatScreen` (`applyState` held on the screen, card sync on `.combat-stage`), `CombatUnitCard` (status pips), `CombatLogView` (the ticker), `RoomStatusPanel`, `RoomSheet`, `RoomView` (the forecast slot), the map's route chip and the Quest Log. `ItemPopup` and other render-on-open popups don't subscribe and need neither.

## World map (three.js)

`client/src/ui/ThreeWorldMap.ts` renders the world map with **three.js (WebGL)** plus a sibling HTML overlay. It keeps the camera, input, uploads and overlay; `client/src/ui/MapBaker.ts` paints layers to offscreen canvases and owns no GPU state; `client/src/ui/mapTerrain.ts` holds the pure decisions.

**Loading.** `MapScreen.createMap` imports the map with `await import('../ui/ThreeWorldMap')` behind an in-flight guard, so three.js is not in the main chunk; `preloadMapCode` fetches the chunk when idle unless Save-Data is on. While it loads `.map-status-card` says "Charting the map…"; an import or WebGL failure turns it into a retry card. The renderer runs with antialias, depth and stencil off and DPR capped at 2. On `webglcontextrestored` the coast is re-baked and the map redrawn.

**Layers**, bottom to top:

1. **Sea.** A plane with `/parchment-artwork/{mapId}.png`, uploaded per map in the admin Maps tab. `loadParchment(mapId)` reloads it on a map switch and drops a load the switch superseded; the fallback is seamless ink-navy noise (`createSeaFallbackCanvas`). The plane follows the camera at 70 %, so the sea shifts only 30 % of what the world does and reads as deeper.
2. **Coast.** A 1/8-res black silhouette offset down 14 world units at alpha .5, with no blur. On the procedural sea only, it adds a soft shallows glow.
3. **Terrain.** No fog baked in. In y order, each room is one `drawImage` of a sprite keyed by type and `hexVariant(col, row)` (three variants, ±4 % lightness): authored colour, a top-lit rim, and a stamp from `terrainMaterial(color, traversable)` (`water`, `foliage`, `rock`, `sand`, `ember`, `plain`), which is derived from the authored colour and never from a per-type table. A type's authored icon draws only when `isLandmarkType` says the type is rare on this map (at most 4 rooms or 2 % of them), so no emoji repeats across the map. Art wins over all of this: `/tile-artwork/{id}.png` on explored rooms, then `/tile-type-artwork/{type}.png`, cover-fit, replacing fill and stamp while keeping rim and edges. One batched edge pass draws same-type lines, different-type lines, ivory foam where water meets land, 7-unit skirts on lower edges above empty or water, and dashed ivory zone borders between walkable rooms.
4. **Fog.** A quarter-res canvas of ink, punched out of one full-map fill so neighbouring rooms never show a seam. It covers art too. `computeFogLevels`: explored in the current zone 0, explored elsewhere .28, unexplored in a known zone .62, unknown zone .86. A blocked room copies its most revealed walkable neighbour, so coasts open as you explore; deeper blocked rooms fade out one level per ring.

**Bake triggers.**

- Terrain: first show, map change and `rebuildFromCache`. It is time-sliced at 8 ms a frame, the deadline checked per room, with one upload at the end. Opening the tab bakes nothing: `snap` moves the party token without a tween.
- Exploring and crossing a zone re-bake fog only. `buildGridFromCache` doesn't depend on unlocks, so an unlock sets `fogDirty` and `markersDirty` without a rebuild.
- Coast: any grid rebuild, sea art arriving or failing, and context restore.
- Scale (`bakeScale`): `min(1, 8192 or the device limit / longest side, sqrt(16e6 / area))`; small maps on 2x screens bake sharper, up to scale 2 and 6 MP. `capabilities` is read lazily because the test stub lacks it.

**Room art lifecycle.** No list says which rooms have art, so every request may be a 404. `MapBaker.requestArt(view)` loads type art for every type, and room art only for explored rooms near the camera, nearest first, with at most 12 images held. An image is decoded (`img.decode()`) before it is reported ready, painted into the retained terrain canvas with its neighbours, then released; a re-bake loads it again from the HTTP cache. 404s are remembered for the session, across map changes too, until a world update calls `forgetFailedArt`. Patching waits out gestures and has the same 8 ms budget. Each upload is the whole terrain texture, so uploads wait for a 1.5 s lull in arrivals, 5 s at most. A full re-bake happens only for type art touching over 30 % of the map.

**Overlay.** `.three-map-overlay` sits over the canvas and hosts every dynamic element. It carries a single `transform: translate(W/2, H/2) scale(zoom) translate(-camX, -camY)` mirroring the camera, so one style write moves every child; children are positioned in world coords and centred with `translate(-50%, -50%)`. `will-change: transform` is on only during gestures, so text re-rasterizes at the settled zoom. Z-order, low to high: hover, selected room, route, quest targets, zone labels, markers, flags, party token.

- `--party-scale` (1/zoom) is written per frame on the token alone. `--map-zoom` inherits through the whole overlay, so it is written only when a zoom settles (`settleZoom`).
- `data-lod` is written on threshold crossing (`lodForZoom`). `far`, below .55: markers collapse to 8px pips and flags, badges and keys hide. `near`, above 1.2: zone labels hide.
- Party token: 36px, counter-scaled, topmost (class art over class icon, initials without a class; gold ring), moved by a 400 ms transform with no pulse. `data-snap` skips the tween.
- Route: one SVG with a dashed polyline over a dark under-stroke, plus a gold pin (`updatePathOverlay`).
- Zone labels: one per unlocked zone at the free explored room nearest its centroid. `pickZoneLabels` puts the current zone first, then the most explored, checks marker boxes at the current zoom, steps through up to 10 rooms, and leaves a label out when none is free.

**Tooltip** is a separate cursor-positioned `.canvas-map-tooltip` element (no map transform), desktop only (touch moves always pan). For an explored room it lists `{zone}: {room}`, one line per room action, then `👥 N players here` — a count, never names; names are revealed only by clicking the room. Unexplored rooms show `{zone}: Unexplored Room` and nothing else.

**Hex slots**: each room's overlay children keep to fixed slots so they never stack — other-party flag top-centre, player-count badge top-right (anchored at its left edge so it grows outward), 🗝️ delving key top-left, room-action marker bottom-centre, party token in the middle. Markers and badges counter-scale from `--map-zoom` as the map zooms out, markers by `clamp(1, 0.75 / zoom, 1.8)`, so they stay legible at `MIN_ZOOM`.

**Render-on-demand**: there's no always-on RAF loop. `requestRender()` schedules a single render on the next animation frame, coalescing multiple state pushes into one. An anim loop runs only during a camera tween (follow, recentre, zoom, spring-back). Party movement lives entirely in CSS, so it drives no JS or WebGL work. Idle map screens cost effectively zero.

**Camera.**

- Default zoom is .65 when the viewport's short side is under 600px, otherwise 1, stored under `mapZoom2` and written at gesture end. Resizing keeps the pan.
- The camera follows the party: when it leaves the inner 60 % of the view (`outsideFollowFrame`), one 300 ms tween. Dragging or keyboard panning turns follow off and lights the recentre button (`setOnFollowChange`). `focusOn` also leaves it off; `recenterOnPlayer` resumes it.
- `revealRoom` nudges the camera just enough for a room to clear the docked sheet, and re-runs on resize.
- A press during a tween holds the camera where it was last drawn (`stopCameraAnim`), so a tap hits what is on screen. A touch sequence that ever had two fingers down never ends in a tap.
- `MapScreen.focusRoom(roomId)` pans to a room and selects it. It waits if the map hasn't loaded, and a room on another map gets a toast instead.

## Room actions

`client/src/ui/RoomActions.ts` is the single vocabulary for what a room offers, shared by the map markers, the tooltip, the room sheet, both RoomView states and the room status panel. `actionLabel` spells an action out; `actionShortLabel` gives the one word a round chip shows on phones. `getRoomActions(room, lookups, quests)` takes `quests: QuestMarks` (`questMarks(state)` → `{ ready, available }`: ready from active quests with status `ready`, available from `state.availableQuestIds`) and returns, in order: the NPC (its own emoji; detail "Quest ready to turn in" plus a gold `?` pip when one of its `questIds` is ready to turn in, otherwise detail "New quest available" plus a green `!` pip when one of them is available — `questPipClass(action)` picks `.quest-ready-pip` / `.quest-available-pip` for every surface), the shop (🪙 if it sells items, 🤝 if it only hires henchmen, detail "Henchmen for hire" when it does both), the dungeon entrance (🗝️), and one travel point per map transition (🌀, named after the destination room, else its map, else "a passage"). Ids that don't resolve are skipped. Lookups come from `WorldCache` (`getNpc`, `getShop` → `ShopSummary` from `/api/world`, `getDungeon`, `getTileByGuid`, `getMaps`), so remote rooms need nothing beyond the login payload.

**Explored rooms only**: markers, tooltip lines and the remote popup's list appear only on rooms `worldCache.isUnlocked` (the same rule that reveals a room's name). The map draws one marker per explored room with at least one action — up to three icons on a dark pill, then `+N`; several exits collapse into a single 🌀. `ThreeWorldMap.updateMarkersOverlay` rebuilds markers only when `markersDirty` is set: unlocks, map switch, content reload, or a changed `questMarkerKey` (sorted ready ids, available ids and quest targets), not every tick. Far zoomed out they collapse to pips (see World map).

## Quest destinations

`client/src/ui/QuestTargets.ts` `pendingVisitTargets(activeQuests, questDefinitions)` maps each room GUID a visit objective still needs to the quests sending the player there, skipping quests already ready or completed. `ThreeWorldMap` outlines each target on the current map (resolved with `WorldCache.getTileByGuid`; targets on other maps are skipped) with a static dashed green hex in the `.three-map-quest-targets` layer, above the route and below the markers, and the hover tooltip adds a `📜 {quest}` line per quest. **Explored rooms only**, like markers: an unexplored destination stays unmarked until the party explores it — exploring is part of the quest — and the outline appears with the marker refresh that the unlock triggers. Quest text names a visit target as "{room}, {zone}" (`QuestText.roomText`; fallbacks "a room in {zone}" and "a specific room") — never coordinates.

## Map toast

`client/src/ui/MapToast.ts` `showMapToast(container, msg)` is the one toast on the map: move refusals (`move_blocked`), the client-side refusals (in a dungeon, not owner/leader, offline), "You can't walk there" on a tap on a blocked room, and `dungeon_entry_refused` errors that arrive while `DungeonEntryPopup` is closed (an open popup shows them itself). It sits top-centre on phones, under the route chip. From 768px, where the room status card takes the top-left, it sits bottom-centre, 64px up, or 176px up over a bottom room sheet so it can't cover Go. One toast at a time; a new one replaces it. It stays up a fixed `MAP_TOAST_MS` (6 s, the same as notification toasts), passed to the CSS fade as `--toast-ms`, and a tap dismisses it sooner.

## Room status panel

`client/src/ui/RoomStatusPanel.ts`, owned by `MapScreen`, shows what the party's current room offers as chips that run the same handlers as the RoomView buttons (`MapScreen.runAction` → `talkTo` / `openShop` / `enterDungeon` / `enterTransition`, with the same in-dungeon and owner/leader checks). NPC chips carry the same `?`/`!` pips as the map. Under 768px a Travel chip first opens a `confirmDialog` naming the destination (`MapScreen.runStatusChip`), because a round chip shows only one word; from 768px the chip already spells it out and goes straight there. Extra chips: `👥 N` when players outside your party share the room (opens the current-room RoomView, where names are listed), and a non-interactive `🗝️ {dungeon} · Floor x/y` while delving. Desktop (≥768px) is a labelled card top-left with a `{zone} · {room}` header; mobile is round chips bottom-left, each with a one-word label under it, lifted 112px over a bottom room sheet. Both are hidden when there are no chips, and `data-controls` on `#screen-map` hides the panel when the map is too short for it. The DOM is replaced only when the content key changes, and never mid-press (`deferWhilePressed`), and taps are stopped (`pointerdown`/`mousedown`/`click`/`touchstart`) so they don't pan or click the map — `mouseup` is deliberately left alone so a map drag released over the card still ends.

## Room sheet

`client/src/ui/RoomSheet.ts`, owned by `MapScreen`, is what a tap on any other walkable room opens: a selection outline (`setSelectedRoom`) plus a non-modal panel docked in `#screen-map`, so the map keeps panning behind it. `MapScreen.syncScreenLayout` writes two attributes from the map's own size, because the chat column can take half the viewport:

- `data-sheet`: `bottom` below 720px of map width (112px tall), `side` from there (320px wide on the right, as tall as its content, adding room art and the "Here now" player list). The zoom controls lift or step aside to stay clear.
- `data-controls`: `full`, `some` (recentre button only) or `none`, from the map height left over the sheet.

A `ResizeObserver` on the screen re-syncs both and re-runs `revealRoom`.

The panel shows the room name, the first action's name, zone and player count, action icons with their pips, a forecast chip with its verdict word (debounced 250 ms, same `roomForecastState` rules as RoomView), Go, and Details (opens RoomView). Tapping the selected room again is Go through `tryMove`, so refusals still toast; a closed socket shows `OFFLINE_NOTICE` and leaves the sheet open. Your own room opens RoomView directly. An unexplored room shows name and Go only. In a dungeon Go is disabled and reads "Leave the dungeon before traveling". Taps are stopped the same way as on the status panel. The sea, the X, Back and Escape dismiss it (`registerDismiss`, no focus taken), as do leaving the screen and a map change. `update()` repaints from pushes under `deferWhilePressed` and restarts the forecast only when its target changes.

## RoomView

`client/src/ui/RoomView.ts` is the full room card, opened by tapping your own room, by the status panel's players chip, and by the room sheet's Details. Under 768px it docks at the bottom at 85dvh. It has three states:

- **Current room (you're here)** — background image (`/room-bg-artwork/{roomId}.png`, then `/room-bg-artwork/{zoneId}-{col}-{row}.png`, then `/room-bg-artwork/{zoneId}.png`), party-grouped player list (your party in a gold-bordered box, then one bordered box per other party), one button per room action (the shop button shows `/shop-artwork/{shopId}.png`), click any player to open the user popup. While the party is walking a route (`state.party.path` non-empty) a **Stop here** button sends a move to this room: the server clears the route if the party is still on it, or walks it back if it has already moved on.
- **Remote room (explored)** — smaller popup with name, an "In this room" list of the room's actions (informational), the same party-grouped player list (when other parties' players are on the room), and a "Go to room" button. The popup scrolls when a room holds many players.
- **Undiscovered** — the same small popup with an "unexplored" hint. The map no longer reaches it, because the sheet offers no Details on an unexplored room.

Grouping logic lives in `RoomView.groupPlayersByParty` and depends on `partyId` arriving on each `OtherPlayerState`. Each rendered room passes through `renderPartyBox(members, label, partyClass)`.

**Forecast slot.** An optional last constructor argument (a `RoomForecastProvider`; tests still construct `RoomView` with two arguments) adds a forecast chip after the header of the current room and after the name of an explored remote room; tapping it opens the details popover. `forecastTileId` and `updateForecast(tileId, state)` let `MapScreen` push results in. `MapScreen` forecasts only explored, walkable rooms, and not the current room while in a dungeon. The room target's `tileId` is the WorldCache tile `id` (room GUID).

Travelling from a remote-room view to your party arriving at that room triggers an arrival expand animation (`.room-view-arrival` class with timed CSS transition). `MapScreen.showRoom` sets `roomView.actions` before showing: for the current room, `MapScreen.currentRoomActions` (shop only when `state.shopDefinition` is present, named from it; dungeon and travel dropped while `state.dungeon` is set); for a remote explored room, `getRoomActions` on its tile. Every button goes through one `onAction` callback into `MapScreen.runAction`.

## Dungeons (client)

When the current room is linked to a dungeon (`tileDef.dungeonId`, looked up via `WorldCache.getDungeon(id)` — catalog fetched once from `GET /api/dungeons`), `RoomView` shows an "Enter {name}" button. Tapping it opens `DungeonEntryPopup` (on `ModalStack`; a header, one scroll body and a fixed footer with status and 44px actions, docked at 85dvh on phones with the forecast and requirements above the lore): flavor, floor count, requirements preview, a forecast card (verdict + headline, likely range, first-try %, reasons, sample size), a floor strip (boss, checkpoint, cleared, resume flag and per-floor %), "Resume: Floor 3 · Checkpoint 2 · 2 retries left" when the forecast key carries a resume point (`parseDungeonResume` reads `…|dungeon:<id>:<floor>:<phase>:<wipes>`; no client-state field holds stored checkpoints), and warning copy that switches to the checkpoint text ("Falling on the boss floor regroups your party at its last checkpoint…") when a floor has checkpoints. Non-leaders see it read-only with "Your party leader's progress decides where you start." and a disabled Enter.

**Eligibility preview**: `previewDungeonEntry(dungeon, state)` (`client/src/ui/DungeonEntryCheck.ts`) runs the shared `validateDungeonEntry` — the server's own validator, so the wording matches — over the party's players: levels and classes from the members' resolved `level`/`className` (else `social.allPlayers`; the viewer from `state.character`), and the viewer's own required item with the server's rule (unequipped when consumed on entry, otherwise owned). Other members always count as holding the item, since the client can't see their bags. If any member can't be resolved it returns `null` and the server stays the judge. Henchmen are never members, so they never block or count toward party size. When the preview blocks entry, Enter is disabled and a visible "⚠ {reason}" line sits right above it (visible text, not a tooltip — mobile has no hover). The popup re-evaluates on every push, so levelling up or a party change re-enables Enter without reopening it. If the party has henchmen, a line says they'll wait at the entrance. The item name comes from `state.itemDefinitions`, else "a key item", so it can differ from the server's wording for an item the viewer has never owned.

**Entering**: Enter sends `enter_dungeon` once and shows "Entering…" until `state.dungeon` is set (the popup closes), a `dungeon_entry_refused` error arrives (shown inline, retry allowed), or 5 s pass ("No answer from the server. Please try again."). The popup also closes when the party leaves the entrance room. Entry is server-authoritative; every `enter_dungeon` refusal carries `code: 'dungeon_entry_refused'`, shown by the popup while it's open (`isOpen`) and as a map toast otherwise. While inside a dungeon, `ServerStateMessage.dungeon` (`DungeonRunInfo`) is set: the combat header shows the dungeon name, a floor badge (`F3/5`, or `BOSS 5/5` on the last floor) and a **Leave** button (`.combat-dungeon-leave`, owner/leader-gated like Run) in place of Run — on a checkpoint floor with a fight under way it first opens a `ModalStack` confirm ("Leaving now counts as a defeat and uses up one retry. Leave anyway?", or that the checkpoint will be lost when no retries are left; `leaveDungeonWarning`), and `MapScreen.tryMove` blocks overworld travel until the party bails out. See `docs/architecture/content.md` → Dungeon system for the server side.

## Multi-map travel (client)

The client renders only the map the party is on. `ServerStateMessage.currentMapId` drives `WorldCache.setCurrentMap`; when it changes, `ThreeWorldMap` rebuilds its grid from the new map's tiles, recenters the camera, snaps the party token (no tween across the discontinuity), and filters the other-player flag overlay to that map (`OtherPlayerState.mapId`). When the current room has `transitions`, `RoomView` shows one 🌀 "Travel to {destination}" button per exit (destination names resolved via `WorldCache.getTileByGuid`); tapping one sends `enter_transition` with that target `tileId` (owner/leader-gated, blocked inside a dungeon). The button goes straight there; only the phone's status chip confirms first (see Room status panel). Transitions may be gated (see `docs/architecture/content.md` → Room entry requirements), but the check is server-authoritative and a refusal comes back as a `move_blocked` message that surfaces in the same map toast as a blocked move. The client cannot preview these gates — party members' equipment and completed quests are not in `GamePartyMember` (their level and class are), and gate items/quests the player has never encountered have no name in `itemDefinitions` — so transition buttons stay enabled. See `docs/architecture/content.md` → Multi-map for the server side. (A zoomed-out overworld/map-select for players is out of scope — issue #168.)

## Hero screen

`CharItemsScreen` (screen id `items`; legacy sessionStorage `activeScreen=character` migrates on load) is three panes that `data-hero-tab` on `.charitems-content` toggles with no rebuild: **Gear, Skills, Stats**. The choice comes from the segments or `setSubTab(gear|skills|stats)`, is remembered in sessionStorage `heroTab`, and each pane keeps its scroll position. The Gear segment counts mailbox items plus trades waiting on you; Skills shows a dot when an unlocked slot could be filled. Layout follows the screen's width through the `hero` container: from 720px Gear is two columns with a sticky loadout and a `hero-summary` card (XP, equipped skills, links to Skills and Stats), from 560px the loadout is a compact row, and under 300px gear drops to four columns.

**Gear**, top to bottom:

- Mailbox and trades waiting on you, when there are any.
- A 72px banner: a fixed 52px portrait (`/class-artwork/{class}.png`, no layout shift), class, level and condensed ATK/DR/MR/HP (click to show a tooltip; Escape and Back close it).
- 12 slots in a 6×2 grid (`.items-equip-col { display: contents }`). An empty slot opens a list of matching bag items (`showSlotPicker`; main hand also lists two-handers; usable first, each row with Equip or "{class} only"). An equipped item's popup has Change, which opens the same list.
- The inventory, then sent trades.

**Inventory.** `renderItemCell` (`.item-cell`) puts the name under each square. Rarity rings are static, and gear the class can't use is dimmed (`canClassEquipItem`). The grid groups items with visible headers when sorted by Rarity or Type (Gear, Materials; Newest stays chronological); the sort is saved per username in localStorage. A stack change patches one badge in place (`patchInventoryCounts`, `writeItemSquareQty`), and only a new item id rebuilds the bag. `content-visibility` sits on cells rather than groups, because one group can span the whole bag.

Clicking an item opens a popup with full details and equip/unequip/destroy actions, plus a comparison with what equipping it would replace; Cancel on either Destroy prompt returns to the item. The comparison is `renderEquipCompareBlock(newDef, equipment, itemDefs)` (`client/src/ui/EquipCompare.ts`, shared with the shop): it compares against every item the shared `getItemsDisplacedByEquip` reports, so a two-handed weapon is compared against main hand plus offhand (summed, names joined with " + ") and a one-handed item against an equipped two-hander. It renders nothing when the slot is empty. `showItemPopup` / `closeItemPopup` (`client/src/ui/ItemPopup.ts`) add an X, register on ModalStack, and on phones dock at the bottom at 85dvh with sticky actions; Craft uses them too, and the Social profile wraps `renderItemPopupContent` in the same `.item-popup-overlay`.

**Skills.** Full rows with descriptions, one per slot (slots per the class's content-driven slot schedule, fetched via `WorldCache.getSlotSchedule`). Clicking opens a picker with all unlocked skills of the matching type plus any skills currently granted by equipped items/sets, with no auto-shuffle on placement; selectable rows are role buttons and the first takes focus. Skill points are gone — skills auto-unlock at each skill's content-defined `unlockLevel`; equipping the slots is the only constraint. Skill slots, the skill picker and the Social player profile show each skill's card-type chip plus `CD Ns`, cast time and trigger, rendered by `client/src/ui/SkillCardChip.ts` (`renderSkillCardChip` / `renderSkillCardMeta`). See `docs/architecture/content.md` → Skill system for the full content model. For Guard/Bless-style rating options `skillComputedLine` appends the exact on-level mitigation ("≈50 % vs same-level enemies").

**Stats.** Attribute rows with explanations, XP numbers and the XP-rate counter, the class blurb and the Bestiary card.

**Bestiary.** A card on Hero › Stats (`BestiaryCard`) shows the kill-mastery summary (discovered / mastered), the 3 entries closest to their next rank and "View all ›", which opens `BestiaryModal` (on `ModalStack`): search, sort (Closest / Kills / Rank / Name), progress bars, rank stars, "Next rank at 250" and the damage bonus. Level badges appear only for authored levels, coloured by con relative to the viewer. The card is keyed on what it shows (counts, level, its 3 rows), not the global kill version, so kills of other monsters don't touch it. While open, the modal re-renders when `mastery.version` moves, at most once per `BESTIARY_REFRESH_MS` (1 s). Both patch rows in place by monster id (`syncBestiaryRows`): portraits, the View all button and focus survive a refresh.

**Mastery toasts.** `MasteryToasts` toasts a live rank-up worth a moment (`isMasteryMoment`) by comparing `mastery.recent` with the last rank it knew (seeded from snapshots and the bestiary; snapshot states never toast, ranks gained while away belong to the recap). A monster it has never seen counts as rank 0 only when `mastery.discovered` grew by at least as many unseen monsters, so a boss's first kill (rank 1) toasts while an old kill the client hadn't loaded yet does not. The toast is `role=status`, sits on `ModalStack` and opens the bestiary when tapped.

## Craft screen

`CraftingScreen` is separate stable sections (head, queue, segments, recipes), each written through `setHtml`. It joins `state.crafting` (queue, progress, skill) with `state.craftingCatalog` (recipes and their item definitions). A 1 Hz timer runs only while a job runs (`syncProgressTimer`) and fills the bar by `scaleX`. ## Chat

`client/src/ui/ChatPopout.ts` (pure logic in `chatModel.ts`, the phone preview in `ChatStrip.ts`, styles in `chat.css`) mounts into `#chat-popout-root`, a flow child of `#app`: chat is docked in the shell, not a floating window. `body[data-chat-open]`, `body[data-chat-layout]` (`sheet`, `full`, `column`) and `body[data-chat-typing]` drive the layout from CSS.

**Layouts.**

- **Strip preview** (phone, closed): `ChatStrip` paints inside the strip's button: channel dot, sender, ellipsized text, count pill. Tapping or swiping up opens chat. A newest unread DM pins over public lines; filtered channels, blocked senders and your own echoes are excluded; server lines show dimmed and never count. The count compares `timestamp` to localStorage `chatLastSeenAt`, seeded on first run from the newest backlog message so the server's clock decides. It repaints at most once a second.
- **Sheet** (phone, default): the root takes `--chat-sheet-height` (`clamp(200px, 36dvh, 300px)`) in flow, so the screen resizes once and the panel slides by transform. No scrim, the nav stays usable, no autofocus. On Battle the skill bar and ticker hide so the stage keeps its space. X, swipe down, Back and Escape close it.
- **Full** (the expand button or swipe up, persisted in `chatPopoutMobileLayout`): the root covers `#app`. `navigate` closes it through `closeIfCovering` so that what a navigation brings up can be seen; the saved layout survives.
- **Column** (the grid layouts): a docked column, open by default unless closed before (`chatPopoutOpen` stores `0`/`1`), with autofocus on fine pointers. The rail's Chat tab shows the count while it is closed. Outside typing, Back closes it only in short landscape, at any width (`isLandscapeColumn`); a taller desktop column stays.

**Stack.** `syncStack` keeps chat's z-index and dismiss in line with the layout. Only `full` and typing get a z-index (`setRaised`), because a flow item with one traps the sheet under the nav. The sheet, `full` and typing register a dismiss; the column suspends it (`suspendDismiss`). Only expanding promotes chat in the order, so it never jumps over a popup opened since.

**Keyboard** (`pointer: coarse`). Composer `focusin` sets `body[data-chat-typing]`, pins `#screen-container` in px so the stage and map don't resize, and fills `#app` with the root; the `visualViewport` handler in `main.ts` then carries the composer. The exit waits 150 ms so tap targets don't jump. It also exits when `visualViewport` shows the keyboard went away while the input kept focus (Android), and on rotation.

**Header and composer.** Row one has All, Party, Guild and DMs tabs with unread dots; a filter icon (a popover with seven toggles, `chatPopoutFilters`, honoured only by All, since Party, Guild and a thread are explicit choices); expand; close. Party and Guild leave the tabs and the channel list when solo or guildless (`chatMembership`). Row two is the native `.chat-popout-channel` select styled as a chip, locked on Party and Guild and hidden on DMs; an input (`enterkeyhint=send`, maxlength 500; 16px, or `--fs-sm` on a fine pointer from 860px); Send, which keeps focus. The composer is never rebuilt, so focus and typed text survive.

**DMs.** A thread list, then a thread. `canonicalUsername` takes a known player's exact spelling, because threads and DM focus compare names exactly. Sent DMs show "to X" on All. Only the thread on screen is reported to `ChatFocusTracker` (`client/src/network/ChatFocusTracker.ts`), so the server suppresses DM notifications for it — see [`notifications.md`](notifications.md).

**Timeline.** `ChatLog` holds at most 500 messages in timestamp order, deduplicated by id; syncs merge and never replace. `sendSyncChat(latestId)` runs on the first state, on open, on tab resume and on reconnect, and the backlog counts toward unread. Rows are appended, not rebuilt, with at most 200 in the DOM. `content-visibility` applies to all but the newest 30, so the jump to the bottom lands on real heights. Scrolled up, it holds position and shows "↓ N new"; past the row cap it keeps only a count and rebuilds on return to the bottom. Paints go through `deferWhilePressed`.

**Sending.** `resolveSendTarget` fills `channelId`: zone sends the party's raw `state.zone` (the server compares the same value), guild sends the guild id, DM the exact username. A failed send keeps the text and says why: `sendChat` returning `false`, a target that can't resolve, or a `chat_refused` error. The server answers sends in order, so `pendingSends` pairs each refusal with the oldest unanswered send. The refused text goes back in the composer only if it is empty and still addresses the same channel and recipient. Otherwise it stays on a "Not sent" line above the composer until dismissed, because refused text must never carry over to a different audience. A connection change or 30 s without a reply forgets a send. The send channel and DM target persist through the server's `chatPreferences` (`sendSetChatPreferences`), not `localStorage`, and are restored once from the first state.

Rows escape everything (`escapeChatHtml`), and `normalizeChatMessage` coerces each field, because saved history can hold values from before the server validated `channelId`. `data-channel-id` appears on DMs only. Blocked senders are filtered here (`isBlockedMessage`); see [`social.md`](social.md) → Chat. Sender names and channel tags are clickable: a sender opens the user popup via `setOnUserClick` with a real anchor, a tag switches the All tab's send channel, and a DM tag opens that thread. Server rows are inert.

## NPC talk popup

The NPC portrait sits in a fixed box with the emoji underneath, hidden once the art loads. The backdrop closes the popup only when both `pointerdown` and `click` landed on it, so a press that starts inside the modal and drifts off it doesn't close it.

- **Eligibility**: Available lists the NPC's offered quests that are in `state.availableQuestIds`, so the popup, the map's `!` and the Quest Log all follow the server's rules and clock. A solo quest while the party has more than one player is listed with `SOLO_QUEST_IN_PARTY_REASON` in place of Accept; other quests stay hidden.

An accept resolves when the quest appears in `activeQuests`; a turn-in when it moves to `completedQuests`, which also queues the NPC's `completionText` speech bubble. Requests settle when the push arrives, not in the held repaint, so a long press can't outlive the reply timer. A `quest_refused` error with the matching `questId` shows the server's reason on that quest's card, next to its button, for 4 s — or, if the refused card has gone from the popup, at the top prefixed with the quest's name; 5 s without an answer shows "No answer from the server. Please try again."; a send that couldn't go out shows the offline notice and sets nothing pending.
- **Leaving the room**: when `state.questGiverNpcId` no longer matches the NPC (the party moved on), the popup stays open with "{npc} is no longer nearby." and no quest sections or buttons — `offeredQuestIds` now belongs to whoever is in the new room.

## Combat screen

`CombatScreen` (`client/src/screens/CombatScreen.ts`) renders the server's real-time fight (see `combat.md` for the engine and protocol). DOM-free logic lives in `client/src/combat/` next to the DOM pieces:

| Module | Role |
|---|---|
| `CombatPlayback` (DOM-free) | timeline player: clock, delayed event/snapshot application, local unit model |
| `CombatLogBuffer` (DOM-free) | merged journal + live log ring owned by `GameClient` |
| `CombatLogFormatter`, `CombatFormat` (DOM-free) | log name colouring, number/time formatting, status pips |
| `CombatUnitCard`, `CombatSkillBar`, `CombatLogView`, `CombatFx` | card DOM, skill bar, ticker + full log, effects layer |

**Layout.** Header (36px: location · dungeon floor/BOSS badge · forecast chip · fight clock · Run or Leave; chip and buttons 30px, all with hit-slop past 44px), the stage (flex), the skill bar (60px, 40px when empty) and the log ticker (48px, exactly 3 whole lines). From 860px the ticker is a 148px log under the stage showing 8 lines, and from 1500px skills and log share one strip, half the width each, instead of stretching across it. The clock reads `–:––` with no fight. Run fills over the first 5 seconds and says "Run becomes available 5 seconds into a fight" if tapped early, or "The next fight is about to start" between fights; the button's width doesn't jump. Run/Leave keep owner/leader gating. When auto-retreat is on, Run carries an 11px 🏳 on its corner (absolutely positioned, so the button never widens) and its title reads "Auto-retreat is on (below 25 %)"; Leave never shows it (auto-retreat is overworld-only). The stage background sits at brightness .75 and layers `/combat-bg-artwork/{tileId}.png` → `/combat-bg-artwork/{zoneId}-{col}-{row}.png` → `/combat-bg-artwork/{zoneId}.png` → `/zone-artwork/{zoneId}.png` → the generated `placeholderUrl(zoneName, { w: 640, h: 360 })`, keyed by the room's raw `zone` tag.

**Stage orientation is pure CSS.** `.combat-stage` is a size container (`container: combat-stage / size`). The stage is vertical when its aspect ratio is below 1.1, or below 1.6 on a stage under 588px wide (enemies on top, party below, both blocks rotated so each side's front faces the centre: `displayRow = 2 − col`, `displayCol = row`); otherwise horizontal (party left, enemies right, monster side mirrored). Placement is by `[data-grid]` on cards; there are no placeholder slots, just one faint tinted plate per `.combat-block`. Container-query breakpoints pick the card mode from the stage's shape:

- **Pills** (round portrait with action ring + name / HP bar / status pips; pips and then names drop as rows shrink) on short stages, with two name lines at stage height 344–479px on vertical stages.
- **Rounded cards** with the name on its own full-width line on vertical stages from 480px tall. Tablet portrait, from 700px wide, raises the caps to a 150px row and a 240px column.
- **Stacked portrait cards** on roomy landscape and desktop stages, with the row capped at 219px and the column at 224px, so the board tops out near 1400x700.
- **Tiles** only on a stage under 588px wide, under 330px tall and wider than 1.6:1.

JS reads the axis only through a cached `ResizeObserver` (for lunge direction and arcs). Under `@media (max-height: 480px)` the ticker hides (tap the header to open the log; `CombatScreen` checks the same media query with `matchMedia`, and the header does nothing while the phone chat sheet is open, because that sheet hides the log too; the docked column doesn't, so `CombatScreen` passes `chatOpen && layout !== 'column'` to `headerOpensLog`) and the skill bar shrinks to 44px.

**Board shape.** A side of one or two units gets `data-roomy` on its `.combat-block`. `CombatScreen.layoutBlock` writes `--track-row*` and `--track-col*` so empty tracks collapse, and each card becomes a `combat-card` size container that sizes itself from its own box, so the art takes the room. The party's portrait caps at 170px, so a solo hero never outgrows the monster. Hit effects anchor on the portrait in roomy blocks. Larger sides keep their rows, and on vertical stages empty columns collapse so names read. Dead units keep their cards, so a side changes shape only when its roster does.

**Status chip.** `client/src/combat/BattleStatus.ts` decides, purely, what the party is doing between fights, and `CombatScreen.paintStatus` writes it with `setHtml` into one 26px line in a strip the grid keeps free: the label gutter on landscape, the centre gap on portrait. It reads "Victory +XP +gold" (`rewardLines`, which handles level-ups), then "Walking to {room}" (discovered rooms only, otherwise "Walking on"), "Fighting here again" or, in a dungeon, "On to the next floor". Defeat and retreat read "Defeated" or "Retreated", then "Regrouping", and with no fight on the board it reads "Regrouping" alone. It is hidden during fights. It appears as soon as playback finishes, ahead of the server's visual, and rewards fill in on the state push. It never reads `party.state`. `status-shown` hides the boss bar. `.victory`, `.defeat` and `.retreat` on the stage tint it, and victory and retreat lift the scrim. With no `battleId`, `.no-combat` dims the cards rather than removing them, and a first load draws the party from `state.social.party` (`syncIdleBoard`).

**Unit cards** (keyed `${side}:${pos}`; party cards are reused across battles with their identity refreshed in place, and only new cards pop in): side-coloured frame (self = gold), action ring, HP bar with trailing damage chip and shield overlay, cast bar (enemy red with a telegraph line + reticle to a locked player target; player blue; paused casts striped; a cancelled cast stays briefly under its stamp: COUNTERED! when the `interrupt` event carries `cardType: 'interrupt'`, which the engine sets only when an Interrupt reaction counters the cast, and INTERRUPTED! otherwise, e.g. for a stun), status pips, greyscale at brightness .7 with a skull when dead. The HP number shows on the self card and on stacked cards. Player portraits layer initials → class icon → class art; monster art uses `/monster-artwork/{id}.png` with a placeholder fallback; henchmen use their emoji/art from `state.social.party.henchmen`. Tapping a player opens the user popup; tapping a monster opens the monster popup (art, description, HP, statuses, current cast, level + con label or "No level set", tier chip, "Built for a group of 3 or more" for boss/raid, and a mastery line from `lastBestiary` or `character.mastery.recent`).

**Levels and tiers on cards.** A `.lvl-badge[data-con]` (glyph + number, e.g. "▴6", aria-label "Level 6, Hard") appears only for **authored** levels, coloured by `levelCon` against the viewer's level through the `--con-*` tokens (pixel-theme `:root`). Derived levels show no number at all. Tier frames use `data-tier`: elite silver ◆, boss gold ♛, raid red ♛. An enraged monster gets `.enraged` (a red aura that pulses three times, then holds). Level, con and tier are part of the card identity key, so a level-up recolours badges; badges scale with the portrait and hide in the smallest layouts.

**Boss fights.** The header shows `[location][BOSS n/m][forecast chip][clock][Leave]`. `.combat-boss-bar` sits in the label gutter, hidden while the status chip takes it: boss name (≤ 38 %), a pooled HP track (`CombatPlayback.bossHpFraction()`) with 🚩 checkpoint ticks that light when reached and a hatched section for HP skipped on a resumed attempt, retry pips from `state.dungeon` wipes/maxWipes (checkpoint floors only), and an enrage slot — ⏱ m:ss (amber in the last 30 s), then 🔥 ×1.6 with a red glow (`enrageSource()`, `enrageDisplay(enrage, elapsedMs)`). `CombatPlayback` keeps `bossPhases` (thresholds from full snapshots; the checkpoint number from every dynamic snapshot and `phase` event, so a dropped message is recovered), per-monster enrage clocks (created from an `enrage` event if no snapshot carried one; enrage is its own status kind and never cleansed), and a `'retreat'` result.

**Forecast chip.** Only in elite/boss/raid fights, once a `{kind:'battle'}` result or `pending` arrives (hidden on `unavailable`/`denied`); it listens to `gameClient.onForecast`, keeps the last 4 battles and picks up an earlier result via `peekForecast`. Always `compact` (ring + number, ≤ 60px); below a 340px header it collapses to the ring (container query on `.combat-header`). Tapping opens `.combat-forecast-popover` anchored under the header; its "Change" button opens Player Options.

**Playback.** `CombatPlayback` renders `PLAYBACK_DELAY_MS` (300 ms) behind estimated server time. The clock offset snaps on a new battle or when off by more than 500 ms, otherwise slews ±15 ms per snapshot; event-only messages only move it forward. Render time is monotonic; events (deduplicated by id per battle) and snapshots apply in timeline order when render time reaches them, and between snapshots the local model is advanced from events and timers are extrapolated (frozen while stunned or dead). Each unit's action ring resets to its own interval: full snapshots carry the static `actionIntervalMs` (players and non-passive monsters), so a fast or slow enemy's ring is right from its first action. Without that field the model starts at the 1 s base and infers the interval from waits observed after an ordinary attack. Reconciliation: `state.battle.combat` is ingested like a message with no events; a new `battleId` resets everything; an older snapshot of the same battle is ignored; a state with no combat clears the fight; more than 1.5 s behind, or activating the screen, jumps to the newest snapshot and keeps only a pending `battle_end`. While the screen is inactive only the newest snapshot is kept.

**`combat_view`.** The server streams `combat` messages to a socket only while it reports the combat view as shown. `GameClient` tracks the value the screen asked for (`sendCombatView`, default `false`) and sends `requested && document.visibilityState !== 'hidden'`. It sends that value on every socket open, bypassing de-duplication, so a fresh or reconnected socket immediately learns the real state. After that it sends only changes. `CombatScreen.onActivate` asks for `true` and `onDeactivate` for `false`. `GameClient` handles `visibilitychange` for every screen: hiding the page sends `false`, and showing it restores the requested value. The server resyncs a socket when the value flips from `false` to `true`, so the Battle screen gets a full snapshot as soon as it is shown. The nav's fighting ring and the map token read `state` pushes, not combat messages, so they keep working on other screens.

**Log.** `CombatLogBuffer` is a 300-line ring keyed `j:{id}` for journal entries (merged from each state message's journal tail) and `c:{battleId}:{seq}:{i}` for live lines from combat messages. While the combat screen is active, live lines are held until playback reaches their message's time so the log never runs ahead of the animation; a resync message (full snapshot, no events) replaces that battle's live lines. After a reload the buffer starts from the journal tail only. The ticker renders the newest 8 lines (`TICKER_LINES`, ≤ 4 renders/s, through `deferWhilePressed` and `setHtml`), which CSS clips to 3 on phones. Expanding opens the full log (`.combat-log-wrapper.fullscreen`, absolute over `#screen-combat` at z-index 50, on `registerDismiss`, closed when the screen deactivates) with pause/resume. Names are coloured with one combined RegExp rebuilt only on roster change, and the viewer's own lines read in the second person ("You hit…").

**Skill bar.** One card per equipped active of the viewer's unit: card-type icon (`SKILL_CARD_TYPE_INFO`), name, a cooldown sweep (`scaleX`) + seconds left, and state READY / WAITING (held) / ARMED (reaction off cooldown) / CASTING, flashing when used. Passive chips follow; with no actives yet the 40px bar shows "Active skill unlocks at level N" as a `data-nav="items:skills"` button. Between battles (or when joining mid-fight) it renders the loadout from `state.character.skillLoadout`. Tapping a card opens a popover with description, card-type blurb, cooldown, cast time and trigger.

**Effects budget.** `CombatFx` draws into `.combat-fx-layer` (and an SVG telegraph layer) using card centres cached per battle and on resize — never measured per event. Floating numbers come from a fixed pool (≤ 24 live, ≤ 2 per unit, hits within 150 ms merge): physical white, magical violet, holy gold, heals green, crits larger with a shake of the stage grid only; DODGE / BLOCK / ABSORB / STUNNED / RESIST / FIZZLE callouts. Attacks lunge toward the enemy side, reactions flip out a mini card (⚡ Instant / ✋ Interrupt), and Intercept draws an arc. With more than 6 cards on the board (`FULL_FX_MAX_CARDS`), per-hit lunge, recoil and flash play only on the player's own card.

**Banners** (`CombatFx.banner(text, tone: BannerTone, holdMs, sub?)`) appear with sparkles only in big fights (`bigFight()`: elite, boss or raid tier, or boss phases); routine fights loop every few seconds and the status chip covers them. The announcer always speaks. They clear within 1.4 s and form a priority queue — retreat/victory/defeat 5 > REGROUP 4 > CHECKPOINT! 3 > ENRAGED! 2 > BOSS FIGHT! 1 > fight 0; a lower-priority banner never replaces a higher one, waits up to 1 s and is then dropped (`clearBanner()` empties the queue). `clearAll(true)` lets a showing result banner finish when the next fight starts under it. Triggers: BOSS FIGHT! at a boss fight's start, REGROUP ("Checkpoint 1 · 2 retries left") when an attempt resumes, CHECKPOINT! with sparkles on each `phase`, ENRAGED! on the first stack only, RETREAT on a retreat result. A visually hidden `.combat-announcer` (`role=status`, `aria-live=polite`) reads out each banner and new `retreat`/`checkpoint` journal lines; the log colours `retreat`, `checkpoint` and `mastery` entries.

**Frame loop.** `--act`, `--cd` and `--cast` are written only on the ring, sweep and fill they drive, `--cd` and `--cast` at an epsilon of .02; HP and shield on ≥ 0.5 % change, and text countdowns at ≤ 10 Hz. Effects run on their own timelines (WAAPI and CSS), so the rAF loop only drives playback: it sleeps once `CombatPlayback.settled` is true, nothing is snapping, `CombatLogBuffer.hasPending` is false and the cards match playback, and a state or combat message wakes it. Nothing in `combat.css` runs forever, which a test guards. The action ring is the one paint-driven timer: see Performance budgets.

**Reduced motion.** `client/src/ui/motion.ts` exports `reducedMotion()` (live `matchMedia`) and `fx(el, keyframes, opts)` (a guarded `el.animate`). When reduced, lunges, shakes, pop-ins, flips, arcs and sparkles are skipped and floaters become short opacity fades; CSS under `prefers-reduced-motion` drops the card pulses and HP transitions, and covers the boss-bar fill, enrage glow/aura, forecast chip and popover animations and recap count-ups.

## ModalStack

`client/src/ui/ModalStack.ts` owns click-order z-index across overlays (from a base of 1500), the order Back and Escape dismiss in, and keyboard focus for modals.

- **`bringToFront(el, dismiss?, { holdFocus? })`** promotes `el` on open and on interaction (`wireFocusOnInteract` attaches it to every press). `dismiss` is what Back and Escape call; a re-promotion without one keeps the earlier one.
- **`registerDismiss(el, fn)`** is for panels docked inside a screen: Back and Escape close them, but their z-index is untouched and they take no focus (room sheet, full combat log, popovers, chat sheet).
- **`suspendDismiss(el)`** makes Back and Escape skip `el` while it holds its place in the order, and **`setRaised(el, raised)`** lifts `el` to the z-index of its place, or drops it back into the page, without moving it in the order. Chat uses both, so reordering never puts it over a newer overlay.
- **`release(el)`** on close. **`dismissTop()`** dismisses the most recently promoted overlay that can be dismissed and returns whether there was one.
- **`dismissModals()`** closes every modal, newest first, so something behind them can be shown (a toast's target, the chat a DM opens). Docked panels stay.

**Focus.** Opening with a `dismiss` makes `el` a modal. It takes focus on a microtask, because callers often append or reveal it after the call: the panel itself with `tabindex=-1`, not its first control, since focusing a text field would raise a phone's keyboard. Tab stays inside. `release` hands focus back to the opener, unless focus has already moved elsewhere, and never to a text field on a coarse pointer. `holdFocus: false` opts out (chat). Toasts and docked panels take no focus, and a repaint that replaces a focused control restores it itself (party grid, shop).

Every overlay on the body or over the shell routes through it and none should hard-code a `z-index`. The one exception is `.notif-toast-stack` at 100000, so a toast stays readable and tappable over any modal. Panels docked inside a screen use local z-indexes.

**Phone sheets.** Under 768px every modal family docks at the bottom at `max-height: 85dvh` with a transform and opacity rise, and 92dvh in short landscape (`popups.css`, `hero.css`, `map.css`, `social.css`, `combat.css`). Bestiary, Recap, Quest Log, notification preferences and patch notes inherit it from the `.player-options-*` shell. The user popup is a sheet below 768px wide or 520px tall.

## Performance budgets

Targets, checked at 375x812 under 4x CPU throttle in a browser with software raster and GL, so read those numbers as relative. Real devices haven't been measured yet.

- **Main chunk**: at most 130 KB gzip. three.js and the map load on demand, and patch notes load when opened. Startup also loads the code chunk shared with the admin page (about 13 KB gzip), which this number leaves out.
- **Phone chrome**: 139px (HUD 44, XP 3, strip 36, nav 56).
- **Idle**: no rAF on the shell, Map or Craft. Battle's loop sleeps between fights (see Combat screen → Frame loop).
- **Tab switch**: no bake, under 50 ms from the tap to the start of the next frame, on first and return visits. A first visit takes about 20 ms on Hero and on Craft (145 and 95 ms before idle prebuild), and 21 and 34 ms if loot changed the state first. Paint can't be done ahead, so that first frame finishes at about 70 ms on Hero and 55 ms on Craft. A tap that beats the idle work, about the first second after entering the game at 4x, pays the old cost. Map's return visit measured 16 ms here, though an earlier run had its frame ending near 60 ms on software GL.
- **Idle prebuild**: once per session, about 30 and 115 ms for Hero and 35 and 65 ms for Craft, each in its own idle slot. It adds nothing to entering the game. A player who never opens those screens still carries their DOM (about 3,000 nodes and 0.3 MB of JS heap for a mid-game character); hidden screens take no style or layout work after that.
- **Map**: at most 2 MiB uploaded while exploring, and at most 60 MiB on a 6 MP map. A large map with art on every room still goes over the memory target. Chunked textures wait for a device trace showing a terrain upload over 100 ms.
- **Animation**: transform and opacity only, with UI transitions at most 200 ms. Game feedback runs longer (party token, follow tween, banners, enrage pulses) but always ends. No `backdrop-filter`. The only infinite animations left are the forecast chip's loading ring and the splash dots.
- **Chat**: at most 500 messages held and 200 rows in the DOM, appended rather than rebuilt.
- **Targets**: at least 44px tall or with hit-slop. **Text**: at least 11px.

**The first layout at boot is cold-start cost.** It is the longest task at startup, about 360 ms, for only about 150 layout objects, and the same layout takes about 37 ms on a reload in the same renderer. A trace puts about 60 % of it in shaping text with cold font caches: 13 system font fallback lookups for emoji and symbols, plus mapping font files. `measureCentres` shows up only because it is the first read that forces layout, and the first frame needs that layout anyway, so moving the read saves nothing. Naming emoji fonts in the stack doesn't help (385 ms), and not laying out the 8 nav glyphs saves about 57 ms, but they are the fallback when nav art is missing. This was traced on Windows, whose font path differs from a phone's, so nothing changes until a device trace shows the same.

**Ranks search needs no fix.** At 1000 players a search that replaces most rows is a 32 ms task, then frames of about 62 and 28 ms, after the 120 ms debounce. An earlier "432 to 618 ms" included a fixed 300 ms sleep in the measuring script, and three runs of unchanged code spread from 445 to 597 ms.

**The action ring is the exception to "transform and opacity only".** `.combat-card-ring` is a conic gradient driven by `--act`, so every write repaints. A transform-only half-disc ring stopped the paint but doubled layerize, and under software raster it cost about 15 to 30 % more main-thread time than the stepped conic with 2 to 12 cards on the board. So the ring stays conic and steps at about 10 writes a second (`RING_STEP_MS`, finer on slow timers so they stay smooth). Those figures may not hold on phones with GPU raster.

## PWA (installability + service worker)

`client/index.html` links `manifest.webmanifest` and sets the theme-color/apple-mobile-web-app meta tags; `client/public/sw.js` (plain, hand-written — not Vite-processed, just copied as-is to the build root) handles app-shell caching and the `push`/`notificationclick` events for the browser-push notification channel. `main.ts` registers it via `registerServiceWorker()` (`client/src/network/PushNotifications.ts`), which no-ops in dev (`import.meta.env.DEV`) so a stale service worker never shadows local changes. `admin.html` deliberately has none of this — only the player-facing client is installable. Full details in [`notifications.md`](notifications.md).

## Image-everywhere convention

`client/src/ui/assets.ts` exposes `artworkUrl(kind, id)`, `placeholderUrl(name, opts?)`, and `renderAssetImg(kind, id, opts)`. Convention: `<mount>/{id}.png`, falling through to generated offline art so layouts always have shape: `placeholderUrl(label, opts)` returns an inline SVG data URI whose colour is derived from the label — a glossy tile with initials (or an emoji `glyph`) for square sizes, a text-free landscape for wide backdrops. Nothing is fetched from a third-party placeholder service.

The kinds themselves live in `ASSET_KIND_INFO` (`shared/src/assets/AssetKinds.ts`) — the single source of truth that the client `AssetKind` union, the server's Express static mounts, the vite dev proxy, the admin upload API, and the MCP asset tools all derive from, so adding a kind is one row there rather than five hand-kept lists that drift. (A static mount still needs a matching dev-proxy entry or the request silently falls through to the SPA index in dev; both lists are now generated from the registry, so they can't disagree.) `artworkUrl` just delegates to the shared `assetPublicPath(kind, id)` rather than spelling `/${kind}-artwork/`, because the three **icon sets** — `class-icon` → `/class-icons`, `slot-icon` → `/slot-icons`, `nav-icon` → `/nav-icons` — predate that convention and serve from their own mounts (a few older call sites in `BottomNav.ts`/`ItemIcon.ts` still hard-code those icon paths). All 17 kinds and their id formats are tabled in [`content.md`](content.md) → "Artwork & imagery".

**Remembered image outcomes**: `renderTrackedImg(src, opts)` (`assets.ts`) renders an `<img class="asset-img">` that starts hidden, so the browser never paints its broken-image glyph; capture-phase `load`/`error` listeners on `document` add `.asset-loaded` (shown, with a 120 ms fade) or try the `fallback` once, then `.asset-failed` (hidden). Outcomes are remembered per URL for the session, so a re-render of art that loaded renders already visible, and art known to be missing goes straight to its fallback — or renders nothing, leaving the caller's own placeholder — with no request and no flicker. `forgetMissingAssets()` runs on a world update and on tab resume so newly uploaded art is tried again. `renderAssetImg` (fallback `placeholderUrl`; class portraits pass the class's `CLASS_GLYPHS` emoji as the tile glyph), item-square art, item popup artwork, NPC portraits and shop henchman portraits all use it. Item squares and the item popup show the item's initials underneath, hidden once the image loads (`.item-square-img.asset-loaded + .item-square-initials`); the image is an absolute overlay so the initials never shift while it loads.

**Icon sets** keep an inline fade (`opacity:0` plus an `onload` that reveals) with a 120 ms `transition: opacity`, and none of them swap to generated art:

- Nav icons (`BottomNav.ts` `navIconHtml`) and slot dogears / empty-slot ghosts (`ItemIcon.ts` `renderSlotArt`) sit over an emoji glyph that shows until the PNG loads and the parent gains `.has-art`. On error the `<img>` removes itself.
- Class and server icons (`inlineIconHtml` via `classIconHtml`/`serverIconHtml`) replace themselves with a glyph span on error.

**Item-square hover** is `filter: brightness(1.15)` plus an inset outline, only under `@media (hover: hover)` and never on empty slots. Don't use a transform there: a scaled square overflows its scroll container and brings up scrollbars. `.item-square*`, `.item-dogear*` and `.item-popup*` rules live in the stylesheets (mostly `charitems.css` and `hero.css`), and rarity rings are static with no keyframes; `CharItemsScreen` injects no styles.

## Browser tab resume

On `visibilitychange` → visible, the client restores its `combat_view` value (see Combat screen) and sends `request_state` for an immediate server response (no waiting for the next battle cycle); the server answers with a state message plus a combat resync when a fight is live. The party token snaps instantly, and the camera re-centres on it unless the player has panned away.

## Other players on map

Each state message includes `otherPlayers: { username, col, row, mapId?, zone, className?, partyId?, inDungeon?, dungeonName? }[]`, holding the players in the viewer's zone (see WebSocket data use). Players on a different map than the viewer are filtered out (so co-located `col,row` on another map don't render). `ThreeWorldMap` renders a flag per occupied tile in the same zone (colour hashed from the tile, so neighbouring stacks read distinctly) with a `×N` badge when more than one player stands there, and a `+N` badge on the player's own tile counting players outside your party so they aren't hidden behind the party token. `groupOtherPlayers` is the one counting rule (same zone, not in my party) shared by the flags, the tooltip count, the room sheet and the room status panel (`countOthersAt`). Positions update on each player's own battle cycle. `partyId` flows through to `TileClickInfo.playersHere` so `RoomView` can group co-located players into one box per party. A party delving a dungeon stays parked at the entrance tile; `inDungeon`/`dungeonName` drive a 🗝️ marker on that tile's flag (`.three-map-dungeon-key`) and a "🗝️ Delving {name}" tag on the party's box in the room popup, so it reads as "inside" rather than "standing around."

## Map controls

Round buttons at the map's bottom right (`.map-zoom-controls`): recentre, lit while the camera isn't following, then + and −, wired to `recenterOnPlayer` and `adjustZoom` (steps .4, .65, 1, 1.5, 2.5). `data-controls` on `#screen-map` drops them when the map is too short. Pinch and wheel zoom on the map itself. With the map focused, arrow keys pan, + and − zoom and Home returns to the party; choosing a room by keyboard would need a room cursor and doesn't exist yet.

**Route chip** (`.map-route-chip`), up while the party walks a route outside a dungeon: `→ {room} · N rooms` and Stop, which sends a move to the current room. The room is named only once explored (`discoveredRoomName`), and only the name ellipsizes, so the count stays readable. It sits top-centre on phones. From 768px it sits bottom left, clear of the status card, 112px up over a bottom sheet and narrowed beside a side sheet. While it is up, the HUD's route line shows the zone instead.

## Desktop font scaling

Font sizes come from an eight-step token scale (`--fs-2xs` … `--fs-3xl`: 11 / 12 / 13.5 / 15 / 18 / 22 / 28 / 36px) defined in `pixel-theme.css :root`; a `@media (min-width: 768px)` block raises every step (11.5 … 42px). Stylesheets use the tokens rather than px sizes. The quest and NPC popups and the Quest Log use only these tokens, so nothing goes below `--fs-2xs`; a guard test in `NpcTalkPopup.test.ts`, reading `pixel-theme.css` and `popups.css`, fails if a `.npc-talk-*`, `.npc-quest-*`, `.quest-card*`, `.quest-pill*`, `.quest-objective*` or `.quest-log-*` rule sets a px font-size under 11.

## Visual style

Modern mobile-game look: **Lilita One** (display: titles, buttons, numbers — weight 400, `font-synthesis: none`) and **Nunito** (body), loaded via `<link>` in `index.html`. Colours, gradients, radii, shadows, button depth, damage/heal colours, rarity colours (legendary gold, heirloom pink) and card-type colours (`--card-attack` … `--card-triggered`) are tokens in `pixel-theme.css :root`; legacy token names (`--bg-panel`, `--accent-gold`, …) alias onto the new palette. Glossy gradient panels with a dark outline and top highlight, chunky buttons with a coloured bottom edge that press down on `:active`, pill tabs, red badge pips with a white outline, glossy progress bars, solid `--scrim` scrims with no `backdrop-filter` anywhere, and a short pop-in on modals (a rise from the bottom on phones). Timers and HP use `tabular-nums`. All UI is vanilla HTML/CSS (no framework).

**Stylesheet cascade** (import order in `client/src/main.ts`): `pixel-theme.css` (tokens, base, older screen rules), `charitems.css` (item squares and popups), `crafting.css`, `mobile-theme.css` (the older component restyle, applied by class name), `combat.css` (the combat screen and monster popup), `components.css` (shared rows, segments, confirm dialog, hover), `shell.css` (HUD, XP hairline, strip, tab bar and rail, grid), `chat.css`, `map.css`, `hero.css` (Hero and Craft), `social.css`, `popups.css` (Settings, onboarding, Quest Log, Shop, NPC and the modal shells they share). The area files override the older themes by load order. `:is()` takes the specificity of its most specific argument, so a few `mobile-theme.css` groups outrank a plain class: docking a modal or restyling a map button needs a more specific selector (`.trade-modal-overlay > .trade-modal`, `#screen-map button.map-zoom-btn`). No screen injects `<style>` blocks from JS. `ItemIcon.ts` emits `--rarity` (and `--item-bg` for an authored `iconColor`) instead of literal colours. The admin dashboard has its own stylesheet and is untouched by this theme.

## Client UI state persistence

Browser refreshes restore the last view from `sessionStorage`: `activeScreen`, `socialSubTab` (saved `users` and `friend_requests` map to Friends) and `heroTab`. `localStorage` holds `chatPopoutOpen` (`0`/`1`), `chatPopoutFilters`, `chatPopoutMobileLayout`, `chatLastSeenAt`, `mapZoom2` and `inventorySort:{username}`. The chat send channel and DM target are server-side (`chatPreferences`), so they follow the player across devices. `RETIRED_STORAGE_KEYS` in `App.ts` lists keys removed on entering the game.
